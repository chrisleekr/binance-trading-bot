# Trailing-trade replay fixtures

The `synthesised/` set is replayed by `__tests__/replay.test.ts` against `trailingTrade.tick`. Each line in a `*.jsonl` conforms to `FixtureLine<TTConfig, TTState, TTBundle>` (see `@app/strategy-core/src/replay.ts`), with `clock`/`rng` swapped for serialisable `__clockNowMs` / `__rngFixed` stamps that the loader rebuilds.

| Directory | Source |
| --- | --- |
| `synthesised/` | Generated by `bun scripts/synthesise.ts` from deterministic seeds + `trailingTrade.tick`. By construction the fixtures match the strategy at the moment of generation; subsequent regressions appear as JSON diffs against the frozen file. |

## Authoritative

These fixtures are the regression check that proves `trailingTrade.tick` does not drift. The synthesised set is the per-pull-request gate (`bun run test:replay`).

## Freezing rule

The set is immutable once committed. A regression that changes a value is acceptable only if EITHER:

1. **The strategy diverged on purpose.** Prepend a `# rationale: <ref>` comment line to the affected fixture (the replay loader skips `^#` lines) explaining why and citing the issue or pull request that authorised the change, then re-run the generator and commit the new payload in the same pull request.
2. **The regression is a bug** and the fix reverts the diff.

Re-running `synthesise.ts` overwrites the file unconditionally — that's why CI replays the _committed_ payload, not a freshly synthesised one. A forgotten check-in is what makes a regression visible.

## Adding a scenario

1. Add the name to `SYNTHESISED_SCENARIOS` and a builder to `SCENARIO_BUILDERS` in `scripts/synthesise.ts`.
2. Run `bun scripts/synthesise.ts --scenario <name>` to write the fixture.
3. Commit the fixture and the script change in the same pull request; the directory-name parity check in `replay.test.ts` will fail until both land.
